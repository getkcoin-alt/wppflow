Task detail

CRM-001 | Plan catalog & pricing (P0) Done

Built. Five plans (Free, Starter, Growth, Business, Enterprise) in the plans and plan_prices tables (migration 018); the server reads them, so no price comes from the browser. The platform admin changes name, numbers, people, features, prices, whether a plan is for sale, and the two limits from CRM-003, from Plans & prices; every change is recorded with what it was before. Owners and administrators see Team → Plans & Billing with a comparison of plans.

Yearly price (decision 1). A year costs ten months: two months free. Monthly stays as published.

Indian prices exclude 18% GST; AED prices exclude 5% VAT. Free and Enterprise have no list price. The platform admin can change any of this at any time.

Trial (decision 5). The Free plan is the trial; no timed trial is offered. The catalogue keeps a trial-days field that nothing uses.

Verified by the plan catalogue and plan admin tests (backend) and the plan comparison and plans editor tests (screen).

CRM-002 | Checkout, gateway & verified webhook, Razorpay (P0) Ready to verify

Built to the specification in 1.1. POST /api/billing/checkout prices the order on the server (plan, yearly or monthly, credit for unused days on an upgrade, GST) and creates a Razorpay order; Standard Checkout opens in the browser; the checkout signature is checked against the order id stored on the server; /api/billing/razorpay/webhook takes the raw body, checks the webhook signature with its own secret, and stores each event id once. One function, settleOrder(), activates the plan; it locks the order, checks status, amount, currency and company, and a mismatch activates nothing and shows to the platform admin. The browser's verify call asks Razorpay's servers about the payment (and captures an authorised one); a job every few minutes recovers lost webhooks; unpaid orders expire after 24 hours; the webhook returns quickly and an unprocessed event is retried. Secrets are only in the server's environment file.

Verified so far: automated tests against a simulated Razorpay: a good payment, a failed payment, a tampered signature, a wrong amount, a wrong company, a duplicate webhook, webhook before verify, verify before webhook, a lost webhook recovered, paying a period already paid. Safeguards were broken on purpose to confirm each test fails when it should. Not yet done: a single call to the real Razorpay. /health reports payments.configured: false until the three settings below exist.

To go live (owner): create Razorpay test keys and a webhook secret and put RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET and RAZORPAY_WEBHOOK_SECRET in the server's environment file, never in chat or in the repository; add the webhook address in the Razorpay dashboard; run the test-mode checklist at the end of this document; confirm in the dashboard's delivery log that the event-id header arrives; only then use live keys.

CRM-003 | Subscription lifecycle + limits (P0) Done

Built. A company's state is worked out from its dates every time: free, original workspace plan, no payment recorded, active, due soon, overdue, expired, changing, cancelling. Late payment (decision 5): seven days of grace after the renewal date, then the company has what Free has (paid features off); nothing is deleted and paying brings everything back at once. While a payment is in progress the order shows as created or attempted and Plans & Billing says it is activating. A smaller plan removes nothing the company already has.

Limits. Numbers, people and features were already enforced on the server. Added now: contacts and broadcasts started per calendar month are limits a plan can carry (blank means no limit; none is set on any plan today, and the pricing page advertises none). When a plan sets one: a person adding contacts by hand, a file import (a batch that would go over is not saved), New chat to a new number, and copying contacts from the phone all stop at the limit with the reason; starting a broadcast beyond the month's count is refused. A customer's message is never refused, and nothing is deleted. A broadcast counts when first started, so a pause and restart is not counted twice.

Usage and warnings. Counted live from the data (no separate counter table, so it cannot drift). Plans & Billing and Contacts show a bar that turns amber at 80% and red at the limit.

Verified by subscription, billing and plan-limit tests, including that each enforcement point fails its test when removed.

CRM-004 | Save/edit contact name (P0) Done

Built. Edit the name from the Inbox panel or Contacts. WhatsApp's profile name is kept in its own field and never overwrites a name a person typed; a typed name can be handed back to WhatsApp's. Numbers are normalised to the international form; saving a number twice returns a clear message pointing at the existing contact (HTTP 409); every rename is written to the audit log.

CRM-005 | Direct WhatsApp message (P0) Done

Built. New chat in the Inbox: type a number, see whether it is already a contact, choose which connected number to send from (only ones the person may use), and get a plain message if the number is not on WhatsApp. A warning shows when the person has not agreed to messages. Sending uses the normal path with delivery states.

CRM-006 | Labels & filtering (P0) Done

Built. Company-owned coloured labels (labels, contact_labels, migration 019), many per contact, bulk add and remove, label filters in Contacts and Inbox with any or all, and a No label filter. Old free-text tags were moved into labels; broadcast audiences still work from them. Labels never cross companies.

CRM-007 | Employee reply analytics (P1) Done

Built. Waits are computed from the customer's first unanswered message to the next human reply; automatic replies, broadcasts, team notes and groups are left out. Median and 90th percentile with a minimum sample of five, the share answered inside the target (a company target and a different target per team), leaderboard, chats still waiting, per-day trend, drill-down to the chats behind a number, and CSV export (formula-safe).

CRM-008 | Inbox quick actions (P1) Done

Built. Filters for waiting and overdue (past the reply target), assigned to me, unassigned, team, label and recent activity; a chat shows how long the customer has waited, red once past the target; pinned chats sit at the top; and a warning appears when a teammate is writing a reply in the chat you have open. Filtering is on the server with paging.

CRM-009 | Follow-up reminders and escalation (P1) Done

Built. A follow-up can be set from a chat that has no lead; assignment to another person (managers) is on the record and tells that person; one that stays overdue past the company's chosen number of hours (default 24, 0 turns it off) tells the owner and administrators once and shows as Escalated in the Today list.

CRM-010 | Customer billing self-service (P1) Ready to verify

Built. Team → Plans & Billing: the current plan with usage; pay now, renew early (the period is never shortened), upgrade (unused days are credited), schedule a smaller plan or cancellation for the end of the period, retry a failed payment; invoices and payment history with PDF download; billing details form. Who may pay and see invoices (decision 6): both owners and administrators. A separate Finance role is therefore not built and not needed.

After payment: the person stays on Plans & Billing, sees "Payment received" with the new end date, and the invoice appears in the list. The second half of the owner's answer to decision 6 (where to send people after paying) arrived incomplete; if a different page is wanted, say which.

Status follows CRM-002: the payment path has only run against a simulated gateway.

CRM-011 | Owner daily reporting (P1) Done

Built. A morning summary of yesterday for owners and administrators in the app (and by email to the owner if switched on): new chats, replies, median wait, share inside the target, chats still waiting, top person, by number, by team and by person, each with the list of chats behind it. Report settings are in Reports.

CRM-012 | Number health (P1) Done

Built. The server asks every number it runs whether it is still connected once a minute and remembers the answer (last_heartbeat_at, misses in a row), since when it has been connected or down, how many times the server brought it back by itself, failed and uncertain sends in the last 24 hours and the last hour, and messages still waiting to leave. The Numbers screen shows this on each card in plain words; owners and administrators see every number, staff their own. Alerts go once per six hours to the number's owner and the managers when a number does not answer three checks in a row, has been down 30 minutes, fails most of its sends (at least five in an hour), or has a message waiting more than ten minutes.

Verified by tests with simulated numbers (answering, refusing, throwing, hanging) and by breaking each rule on purpose. Still to see: on the live server, that the "Last check" on a connected number moves every minute (it asks WhatsApp Web's own isConnected()).

CRM-013 | Automatic lead assignment (P2) Done

Built. Automations → Automatic assignment. When a customer writes to a new chat on a number the company chose, it goes to a teammate: in turn (continuing after whoever got the last one) or least busy. Only people the company put in the rotation, who have not switched themselves Away in the Inbox, and (optionally) only one team, take chats; an optional limit on open chats per person; optional working days and hours in the company's time zone; a returning customer goes back to the owner of their open lead. With nobody available the chat stays unassigned like today. Only the first message of a chat triggers it, so a chat a manager unassigned on purpose is not taken back. Each assignment is on the audit log and tells the person. The existing rule "assign to a teammate" now also gives that person access to the chat.

CRM-014 | AI conversation summaries (P2) Done

Built. Summaries as before (a person always reads and sends; phone numbers and media are not sent; customer messages are data, not instructions). New: a Mood beside the summary, one of positive, neutral, frustrated or urgent with a few words why. It describes the chat, not the person, is shown only with a summary someone asked for, and is dropped if Riwo answers with any other word.

CRM-015 | SaaS super-admin console (P2) Done

Built. On the platform screen: Overview (companies, people, numbers connected, messages sent and received, Riwo use, payments recorded; counts only), Number health (every company's numbers with the ones needing attention first, phone numbers shortened to four digits), Billing audit (money against invoices and a list of what does not add up: payments that did not match, paid at the gateway but not settled here, no subscription record, no invoice, gateway messages not processed, gaps in invoice numbers, bad signatures), and Support access per company. The platform admin still cannot read a company's chats.

Support access that is logged. Looking at a company's team, numbers or account activity needs a stated reason (at least 10 characters) and opens a session of 5 to 240 minutes. The company's owner and administrators are told when it opens, and Team → People lists every session with who, why and what was looked at. Chats, contacts and files are not part of it.

CRM-016 | Razorpay autopay (P1) Ready to verify

Built (decision 4: only for companies that choose it). An owner or administrator can turn autopay on for a monthly plan: a Razorpay plan per Scriwo plan and amount, a first authenticated payment registers the mandate, and each subscription.charged event records one payment through the same path as a checkout payment; repeated events create one period. A failed charge shows as overdue and the company can pay by hand; turning autopay off keeps the paid period; paying by hand while autopay is on is refused with an explanation. Yearly plans are not offered autopay.

Verified against a simulated Razorpay only. Open: confirm Razorpay's current limits on recurring debits; with 18% GST the Business monthly amount (about 17,699 rupees) is above the 15,000-rupee level up to which recurring debits are usually processed without the customer approving each one.

CRM-017 | GST invoices and receipts (P1) Ready to verify

Built (decision 3). Seller details from the GST certificate: SCRIZA PRIVATE LIMITED, GSTIN 09ABICS9865M1Z8, Ground Floor, 4-5, Logix Park, Captain Vijayant Thapar Marg, near Artech Infosystems Pvt Ltd, Sector 16, Noida, Gautambuddha Nagar, Uttar Pradesh 201301 (state code 09). Buyer details per company (legal name, address, state, GSTIN if any) are asked for before the first payment. Tax is shown separately at 18%: CGST 9% + SGST 9% when the buyer's state is Uttar Pradesh, IGST 18% for every other state. Numbers run in a series per financial year without gaps (for example SCZ/26-27/00001); the counter moves in the same transaction as the invoice, so a failed payment never uses a number. A PDF is downloadable by owners and administrators; each settled payment gets an invoice, and a payment recorded by hand gets one on request. The PDF writes amounts as "INR" because the built-in font has no rupee sign.

Before the first live invoice (accountant): confirm the invoice fields, the service code (set to 998314, changeable with SELLER_SAC_CODE) and the series wording.

Dev workflow / definition of done (unchanged)

For every task: (1) inspect existing implementation, (2) agree schema + permissions, (3) implement migration/API/UI, (4) add unit/integration tests, (5) validate in staging against actual WhatsApp channel constraints, (6) attach screenshots/test cases to PR, (7) deploy with backup and rollback plan, (8) mark task Done after owner acceptance.
