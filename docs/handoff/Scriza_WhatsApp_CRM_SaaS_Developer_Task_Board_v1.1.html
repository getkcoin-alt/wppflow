SCRIZA | PRODUCT DEVELOPMENT HANDOFF

WhatsApp CRM - SaaS Launch & Feature Development

Developer-ready backlog | Version 1.1 | 25 October 2026 | Supersedes version 1.0 of the same day

Goal: convert the existing multi-number, multi-agent WhatsApp CRM into a paid multi-tenant SaaS product, then improve contact management, direct messaging, tagging/filtering, and team response analytics.

What changed in 1.1
  • Every task now has a status, checked against the code and the automated tests, not against screenshots. Version 1.0 said the screens were "not backend-verified"; this version replaces that with what was read in the repositories.
  • Several tasks were already partly or fully built (subscription periods and renewals, the AI assistant, follow-ups, contact rename, start-chat from Contacts). Their remaining scope is smaller than the 1.0 effort suggests.
  • CRM-002 is rewritten for Razorpay (orders, verified checkout, signed webhooks, idempotency, reconciliation). Recurring autopay is split out as CRM-016 and GST invoices as CRM-017.
  • Decisions the owner must make before CRM-002 starts are listed at the end of this document (annual price, UAE/AED, GST, autopay, who may pay).

Status key: Done built, tested and live   Partly some of the scope is built   Not started   New added in 1.1.

Product today (read from the code, 25 October 2026)

  • Inbox and numbers: shared live inbox over several linked WhatsApp numbers; staff see their own number's chats and chats assigned to them, owners see all, enforced on the server; assign, resolve, private notes with @mentions; saved replies; alerts when a phone goes offline.
  • Plans: Free, Starter, Growth, Business, Enterprise are enforced on the server (numbers, people on Free, broadcasts, automations, sales pipeline, audit log, API, AI). The platform admin chooses a plan when creating a company and can change it.
  • Subscriptions (new since 1.0 was drafted): each company has a billing cycle, a period and a renewal date; the platform admin records each payment; a smaller plan or Free can be scheduled for the end of the period and is applied by a daily job; owners are reminded once before renewal and once when overdue; nothing is switched off automatically for non-payment.
  • Sales pipeline: board, list and Today list, follow-ups with reminders, a bar in every chat, lead rules, Growth plan and above.
  • Broadcasts and automations: three-step broadcast wizard with consent checks, ten ready-made messages, 14 ready-made rules, keyword / first-message / after-hours triggers.
  • Riwo (AI assistant): reply drafts, improve, translate, chat summaries; company switch, daily allowance, usage shown in Your plan and on the platform list.
  • Not present: any online payment, invoices, reply-time analytics, colour labels, Inbox filters beyond All / Unread / Groups, round-robin assignment.

CRM-002 | Razorpay checkout + webhook (P0) Not started

Build the first paid path with Razorpay Orders + Standard Checkout: one payment pays for one period (a month or a year), which is exactly what the subscription record already models. It reuses the existing recordPayment() so a Razorpay payment and a payment recorded by hand end up in the same place. Autopay is CRM-016.

Flow

  1. The owner opens Plans & Billing, picks a plan and monthly or yearly, and gives billing details if none are saved (CRM-017).
  2. POST /api/billing/checkout (owner only): the server finds the company from the login, reads the price from the plans table, adds tax, writes a payment_orders row (status created) and creates a Razorpay Order: amount in paise, currency, receipt = our order id, notes = company id, plan, cycle. It returns only the public key id and the order id.
  3. The browser opens Razorpay Checkout with that order. Card and bank details never touch Scriwo.
  4. On success the browser posts razorpay_order_id, razorpay_payment_id, razorpay_signature to POST /api/billing/verify. The server recomputes HMAC-SHA256(order_id + "|" + payment_id, key_secret) using the order id from its own record, not from the browser, and compares in constant time. A valid signature shows "payment received, activating" but is not by itself the activation.
  5. Activation happens in one function, settleOrder(), called by the signed webhook (payment.captured / order.paid) or by the reconciliation job. It locks the order row, checks status, amount, currency and company, then calls recordPayment() and moves the order to paid. Whichever runs first wins; the second finds the order already paid and does nothing.
  6. The owner and administrators get an in-app "payment received" notice; an invoice is issued (CRM-017).

Webhook rules

RuleRequirement
EndpointPOST /api/billing/razorpay/webhook, public, mounted before the global JSON parser with express.raw, because the signature covers the exact bytes received.
SignatureX-Razorpay-Signature = HMAC-SHA256 of the raw body with the webhook secret (not the API key secret), compared in constant time. Invalid: 400, nothing stored except a log line without the body.
IdempotencyThe event id (X-Razorpay-Event-Id) is inserted into gateway_webhook_receipts with a unique constraint first; a duplicate returns 200 and does nothing. Events can arrive more than once and out of order, so every handler checks the order's current state.
Replay safetyUnique event id plus the order state check; a replayed old event cannot extend a period twice.
Checks before activatingOrder exists and belongs to the company in its own notes; payment amount and currency equal the order's; payment status is captured. Any mismatch marks the order mismatch, activates nothing and raises an alert for the platform admin.
Failed / pendingpayment.failed records the reason and leaves the company unchanged; the screen offers retry with a new order.
RefundsA refund event is stored and shown to the platform admin; it does not remove access by itself (P1).
Response200 within a few seconds after the receipt is stored; heavy work after responding or by the job.
AuditEvery order, receipt and settlement writes an audit entry; secrets and full card data are never logged.

Reconciliation and recovery

A job every few minutes looks at orders still created or attempted after 10 minutes and asks Razorpay for the order's payments; a captured payment is settled the same way a webhook would. This covers lost webhooks and a customer who closed the tab. Orders with no payment expire after 24 hours.

Configuration (server only)

RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET, RAZORPAY_WEBHOOK_SECRET in the server's environment file, never in the repository or the browser. The mode (test or live) follows the key prefix rzp_test_ / rzp_live_; /health reports whether payments are configured and in which mode. Checkout is switched off when any of the three is missing.

Acceptance

  • Successful verified payment activates exactly one company, once; a duplicate webhook creates no duplicate payment, period or invoice.
  • A failed or pending payment does not activate; a payment for the wrong amount, currency or company does not activate.
  • The company cannot be chosen by the browser: another company's order id returns 404.
  • Activation works when only the webhook arrives, when only the browser verify arrives, and when both arrive together.
  • Paying early never shortens a period; paying for a period already paid up shows a warning first.

Dependencies: CRM-001. Verified from public documentation: webhook signature, checkout signature and the X-Razorpay-Event-Id header (confirm the header in the test-mode delivery log). Everything else is to be proven in Razorpay test mode before live keys are used.

CRM-016 | Razorpay autopay (P1) New

Recurring charge through Razorpay Subscriptions: a Razorpay plan per Scriwo plan and cycle, a first authenticated payment that registers the mandate (card, UPI autopay or e-mandate), then subscription.charged events that each call recordPayment(). Map halted to payment overdue and cancelled to a scheduled end of period; let the owner cancel autopay; keep the manual "pay now" path.

Why it is separate: amounts are fixed on the Razorpay plan, so a price change needs a new plan; and with 18% GST the Business monthly amount (about 17,699 rupees) is above the 15,000-rupee level up to which recurring debits are usually processed without the customer approving each one. Confirm the current limits with Razorpay before building. Yearly plans are not suited to autopay.

Acceptance: one charge, one period, however many times Razorpay repeats the event; a failed charge shows overdue and the retry state; cancelling stops the next charge and keeps the paid period.

CRM-017 | GST invoices and receipts (P1) New

Billing details per company (legal name, address, state, GSTIN if any), an invoice number series, tax shown separately (18% GST for India), a PDF the owner can download, and a receipt for every settled payment. The invoice must match the paid transaction exactly; manual payments get an invoice the same way. The accountant confirms the invoice fields and service code before the first live invoice.

Acceptance: downloadable invoice matches the paid transaction; numbers never repeat or skip silently; only owner and finance roles can see invoices.
